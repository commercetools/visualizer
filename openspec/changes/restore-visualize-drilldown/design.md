## Context

All paths are relative to the repo root `<repo-root>`. The app lives in
`visualizer/` (package.json at `visualizer/package.json`); run every `npm` command from there. New code goes
to `visualizer/src/components/visualize-drilldown/`. Do not edit anything under `$SRC`
(read-only source repo, used only with `git show`).

Glossary (read once):
- **Merchant Center (MC)**: the commercetools admin app that hosts our Custom Application.
- **MC API proxy**: the app never talks to commercetools directly; it dispatches a `sdk` redux action with
  `mcApiProxyTarget: COMMERCETOOLS_PLATFORM` and MC forwards it with the user's token. The token only has the
  scopes listed in `custom-application-config.mjs` `oAuthScopes` (intersected with the user's MC permissions).
  A missing scope is an HTTP **403** at runtime, not a build error.
- **Treemap**: a chart where each item is a rectangle; here all rectangles have the same area (weight 1).
- **Level**: 0 = list of one root type; 1 = entities related to the clicked entity; 2 = related to that one...
- **where predicate**: the commercetools query language in the `where=` query parameter, e.g. `key in ("a","b")`.

## Goals / Non-Goals

**Goals:**
- Same features and behaviour as before (Q1 default), on Nimbus, with i18n en + de.
- Correct under a real MC (403s, empty projects, big projects, slow network) and covered by tests.
- Accessible: keyboard operable, named controls, colour not the only carrier of meaning.
- No foreign copyright code copied; only permissively licensed, declared dependencies.

**Non-Goals:**
- Routing, menu link, Welcome card, `oAuthScopes` edits, `connect.yaml` (other changes).
- URL deep links / persisting drilldown state in the URL (old page did not; `wire-routes-and-welcome` mounts it without props).
- New entity types (orders, carts, shopping lists, quotes, discount codes, ...), editing data, GraphQL migration.
- Dark mode (MC is light-only today); tile colours are validated for light only.
- A table alternative view of the chart (owner question QC3; default: not built, tiles are accessible buttons).

## Decisions

### D1. Treemap: open-source `@visx/hierarchy` (headless) for layout, React renders HTML tiles
Owner decision (2026-10-08, QC1/Q13): "find an open-source replacement" for the hand-rolled d3 code instead of using
`d3-hierarchy` directly or writing our own layout. Candidates were compared on the npm registry (`npm view <pkg> license version
peerDependencies dependencies`, checked 2026-10-08):

| Candidate | Licence | Version / last publish | React 19 | Size (unpacked) | Keyboard / a11y | Drill-down | jest (CJS) |
|---|---|---|---|---|---|---|---|
| **`@visx/hierarchy`** (Airbnb visx) | MIT (deps: `@visx/group` MIT, `classnames` MIT, `d3-hierarchy@1.x` BSD-3-Clause, `@types/d3-hierarchy@1` MIT) | 4.0.0, 2026-06-11 | yes (`^18 \|\| ^19`) | ~49 kB | **Headless**: we render our own `<button>` tiles, so full control of focus, names, tooltip | Yes - we own click handling and state | `exports.require -> lib/index.js` (CJS), dep `d3-hierarchy` 1.x is CJS: **no `transformIgnorePatterns` needed** |
| `recharts` `Treemap` | MIT | 3.10.1, 2026-10-03 | yes | ~7.4 MB (pulls redux-toolkit, immer, es-toolkit, victory-vendor) | SVG; `accessibilityLayer` is for axis charts, custom `content` needed for focusable tiles | `onClick` only, no built-in; custom `content` needed for labels | CJS available, but heavy and duplicates `react-redux` already present |
| `@nivo/treemap` | MIT | 0.99.0, 2025-05-23 (no release for >1 year) | yes (`^19.0`) | ~247 kB + `@nivo/core`, `react-spring`, `lodash` | SVG/canvas nodes, not buttons; tooltip is its own; keyboard support limited | `onClick` + `nodeOpacity`; no built-in | CJS main; many transitive deps, `d3-hierarchy` 3 (ESM) is bundled by nivo |
| `react-d3-treemap` | BSD-3-Clause | 2.0.6 | **no** (peer `^18` max) | - | none documented | built-in zoom | peer dependency conflict with React 19.2 |
| `d3-hierarchy` directly (previous default) | ISC | 3.1.2 | n/a (no React) | small | n/a (we render) | n/a | **ESM only**, needs `transformIgnorePatterns` |

Decision: **`@visx/hierarchy` ^4.0.0**. Why: permissive (MIT, plus a BSD-3-Clause transitive), maintained (4.0.0 released June 2026), React 19
peer range, small, **headless** (it computes the squarified layout and hands us nodes, so tiles stay real `<button>`s with Nimbus `Tooltip`,
visible focus ring and accessible names - the requirement of spec "Treemap rendering"), no ESM-in-jest problem, no style/theme system that would fight
Nimbus, no new state library. The "ready-made chart" libraries (recharts, nivo) draw SVG shapes, so keyboard focus, accessible names and
Nimbus tooltips would need custom `content` renderers anyway, for a much larger bundle.
Old: `d3` imperatively mutates an `<svg>`; text fitting uses `getComputedTextLength()` (needs a real browser,
untestable in jsdom, not keyboard accessible, tooltip hand-rolled with `position: fixed`).
New: `treemap-chart.tsx` uses `import { Treemap, hierarchy, treemapSquarify } from '@visx/hierarchy'` (the package re-exports the d3 helpers, so we never import
`d3-hierarchy` ourselves): `<Treemap root={hierarchy({id:'root', children}).sum(d => d.value).sort(...)} size={[width, height]} tile={treemapSquarify} paddingInner={2} round>`,
and in the render prop maps `treemap.leaves()` to absolutely positioned `<button>`s inside a `position: relative` box. Text fits by CSS
(`overflow: hidden; text-overflow: ellipsis`, `-webkit-line-clamp`) and is hidden when the tile is smaller than 60 x 30 px.
`utils/treemap-layout.ts` is no longer a separate file (no layout code of our own); the "tiny pure helper" that remains is `toTreemapData(nodes)` (weights) in `treemap-chart.tsx`.
Spike result (task 1.3, 2026-10-09): `@visx/hierarchy` 4.0.0 renders in jest (CJS, no `transformIgnorePatterns`), types resolve under React 19 / `tsc`; licences verified (`@visx/hierarchy` MIT, `@visx/group` MIT, `classnames` MIT, `d3-hierarchy` 1.1.9 BSD-3-Clause, `@types/d3-hierarchy` 1.1.11 MIT). Fallback ladder not needed.
Licence: library licences are dependency licences; no source is copied into the repo, so the gate's foreign-copyright source scan is not triggered.
Still, task 1.2 checks the installed tree (`npm ls`, `license-checker`-style one-liner) and the labs gate (change I/H) must see no `Copyright` text of another party in the first 2000 chars of any *tracked* file.
Fallback ladder (decide in task 1.3 within 30 minutes, record the outcome here): (1) `@visx/hierarchy` fails in jest/build/React 19 or licence check ->
(2) `@nivo/treemap` (MIT; nodes via the `nodeComponent` prop to keep `<button>`s - only if it supports HTML nodes in the installed version, else skip) ->
(3) `recharts` `Treemap` with custom `content` -> (4) last resort: direct `d3-hierarchy` ^3 (ISC, needs `transformIgnorePatterns: ['/node_modules/(?!(d3-hierarchy)/)']`) or a hand-written squarify. Any dependency whose licence is not MIT/ISC/BSD/Apache stops the change (ask the owner).

### D2. Keep REST through the MC proxy (not GraphQL)
The relationships use REST predicates and two REST-only sub-resources (`/product-selections/{id}/products`). Porting to
GraphQL would change behaviour and need codegen. Add the explicit dependency `@commercetools-frontend/sdk`
(`^27.11.4`, same major as the other `@commercetools-frontend/*`) because importing a transitive dependency breaks under
strict installs. `restore-entity-diagram` adds the same line - when both changes are applied, keep one line.
New `hooks/use-ct-rest.ts` wraps `useAsyncDispatch` and builds the URI with `encodeURIComponent` (old code used
`URLSearchParams`, which encodes spaces as `+`; unverified against the proxy, `%20` is always valid).
Error shape: the `sdk` rejects with an object carrying `statusCode`; `isForbiddenError(e)` = `e?.statusCode === 403 || e?.status === 403`
(spike in task 2.2 confirms the real shape with msw before relying on it).

### D3. Colours: the old palette is replaced
Old `DEFAULT_COLORS` fails the repo's dataviz validator (`node scripts/validate_palette.js "<hex,...>" --mode light`
of the `dataviz` skill): lightness band FAIL (`#0d3d15` too dark, `#F5A623`, `#a7d350`, `#50E3C2`, ... too light), chroma FAIL
(`#0d3d15`), normal-vision floor FAIL (`#50E3C2` vs `#a7d350` DeltaE 12.9 < 15). It also has 11 colours; the method allows 8.
Rule used: one level shows only the children of one parent (max 5 types), so only types that are siblings must differ;
types that never share a level may share a slot. The 8 slots are `references/palette.md` of the dataviz skill (light):

| Slot | Hex | Entity types (sharing = never siblings) |
|---|---|---|
| 1 blue | `#2a78d6` | business-unit, standalone-price |
| 2 orange | `#eb6834` | store, customer-group |
| 3 aqua | `#1baf7a` | product |
| 4 yellow | `#eda100` | channel |
| 5 magenta | `#e87ba4` | product-selection |
| 6 green | `#008300` | category |
| 7 violet | `#4a3aa7` | customer, associate |
| 8 red | `#e34948` | cart-discount |

Sibling sets that must be distinct (test derives them from `relationships.ts`): {store, associate, business-unit};
{business-unit, product-selection, channel, cart-discount, customer}; {product, store}; {product-selection, standalone-price, category};
{product, category}. All pass with the table. Three slots (magenta, yellow, aqua) are below 3:1 contrast against white: the
"relief rule" applies - visible labels (tile text, legend) and the accessible name exist. Tile ink: `utils/colors.ts`
`getInkColor(fill)` picks `#000000` or `#ffffff`, whichever has the higher WCAG contrast (always >= 4.5 for these fills).
The "Load more" tile is neutral (`neutral.3` fill, dashed `neutral.8` border), never an entity colour.
If the owner prefers Nimbus palette tokens, QC2.

### D4. State and request safety
- `utils/navigation-reducer.ts` (pure, unit-tested): state `{ selectedType, levelIndex, breadcrumbs, search, sort, selectedEntity, hiddenTypes }`
  with actions `selectType`, `drillInto`, `goToLevel`, `goToRoot`, `setSearch`, `setSort`, `toggleType`, `showAll`, `hideAll`,
  `selectEntity`. Replaces ~10 scattered `useState`s and the `console.log` trail.
- `useDrilldownFetcher` keeps its public shape (`levels`, `loading`, `error`, `fetchRoot`, `fetchRelated`, `loadMore`, `reset`) but
  (a) a `requestIdRef` counter - a response is applied only if its id is still current (fixes out-of-order search results),
  (b) an `isMountedRef` guard, (c) `loadMore` reads current data via a ref (old closure over `drilldownData` caused stale appends),
  (d) per-relation try/catch returns `{ failed: [{type, status}] }` so one 403 does not hide the others,
  (e) it never creates a second hook instance: `getEndpoint`, `hydrateExpansion`, search predicates are pure functions in `utils/`
  (old `SearchAndSortControls` and `useAdditionalData` each called `useDrilldownFetcher()` just to reach them - two hidden extra state machines).
- Page effect: fetch root when `selectedType` set and `isAtRoot` and `(search, sort)` change (as old), debounced by submit (search is
  submit-only, no debounce needed).
- Old bug fixed: `multi-level-treemap.tsx` returned early (`if (drilldownData.length === 0) return null`) **before** two `useEffect`s
  (rules-of-hooks violation, lint error `react-hooks/rules-of-hooks`). New code calls hooks first.

### D5. Additional data ("has 3 stores"): local first, queue the rest
`utils/entity-summaries.ts` replaces `ENTITY_DATA_QUERIES`. Each summary is `{ id, local?(entity, ctx) => SummaryValue | null, query?: RelationshipQuery,
format(result) }`. Where the number is already inside the entity returned by the list request, compute it locally (zero requests):
product variants (`masterData.current.variants.length + 1`), product categories, business-unit associates + inherited, business-unit
stores, store product selections, store channels (supply + distribution), cart-discount stores, customer groups (`customerGroup` +
`customerGroupAssignments`), standalone-price discount. Only these need a `limit=1` request reading `total`: customer-group to customers,
product-selection to products / stores, product to standalone prices, business-unit to divisions, store to cart discounts / customers,
channel to stores, category to products / subcategories, associate to business units. Worst case at 20 tiles of one type: 40 requests; a
`runWithConcurrency(tasks, 4)` helper (`utils/concurrency.ts`) limits parallelism; a `Map<levelKey+id, lines>` cache merges results
(old code replaced the whole map on every batch, so "load more" erased earlier lines); a `generationRef` drops results when the level changes.
Dropped as dead: `store->category` and `cart-discount->store` request entries (they had no `RELATIONSHIP_QUERIES` entry, threw inside a
swallowed try/catch, never produced text) and the `customer->customer-group` query (queried `/customer-groups` with a nonsense predicate).
Fixed: `product-selection->product` text read `result.results[0]?.productCount` (field of the selection, absent on the products endpoint) -
use `result.total`. Text is ICU-pluralised messages (`VisualizeDrilldown.summary.*`) not template strings.

### D6. Predicate safety and size
`utils/where-predicate.ts`: `escapeString(s)` replaces `\` then `"`; `quote(s)`, `inList(values: string[], max = 100)` returns
`{ predicate, truncated }`. All interpolations in `relationship-constants.ts` (keys, ids, skus, search text) go through these.
Keys/ids containing quotes cannot occur in ids but can in user-typed search and in keys. The truncation flag is surfaced in the UI note.

### D7. Breadcrumbs: small custom `<nav>`, not Nimbus `Breadcrumbs`
Nimbus `Breadcrumbs.Item` renders navigation links (needs `href`, last item is automatically the non-interactive current page) and has
no collapsing; ours is in-memory navigation with "..." collapsing. A `<nav aria-label>` + `<ol>` of ghost `Button`s with `Home`/`ChevronRight`
icons keeps old behaviour and is simple to test. Last item gets `aria-current="page"`.

### D8. Public interface of the component
`src/components/visualize-drilldown/index.ts`: `export { default } from './visualize-drilldown';` - default export, **no props**, no router
usage (so `wire-routes-and-welcome` can mount it with `<VisualizeDrilldown />` and mock it in route tests). No back-to-Welcome link
(old page had none; the MC menu is the navigation).

## Data flow

```
EntitySelector -- select(type) --> navigationReducer ----------------------+
SearchAndSortControls -- submit/sort -->                                    |  state {type, level, breadcrumbs, search, sort, hidden}
                                                                            v
effect: type && atRoot --> useDrilldownFetcher.fetchRoot(type, search, sort)
Tile click (has children) --> reducer.drillInto + fetchRelated(entity, type, level+1)
Load-more tile --> fetchMore(level, type)           (root: re-applies search/sort; deeper: rebuilds relation query)
        |
        v   useCtRest.get(endpoint, params)  --dispatch(sdk.get)-->  MC proxy --> commercetools REST
        v
levels: DrilldownData[] {level, entityType, entities[], pagination, parent*, truncated?}   failures: [{type, statusCode}]
        v  (current level only)
MultiLevelTreemap --> tiles (@visx/hierarchy Treemap) + legend (counts/totals) + useAdditionalData (queue, concurrency 4, cache)
Tile click --> selectedEntity --> "Entity details" button --> EntityInfoPanel (Drawer)
```

## Relationship queries (must be preserved exactly; ids/keys go through `quote`/`inList`)

| Parent to child | Request |
|---|---|
| business-unit to store | `/stores?where=key in (<bu.stores[].key>)` |
| business-unit to associate | `/customers?where=id in (<associates + inheritedAssociates customer ids>)` |
| business-unit to business-unit | `/business-units?where=parentUnit(key="<key>")` |
| store to business-unit | `/business-units?where=stores(key="<key>")` |
| store to product-selection | `/product-selections?where=id in (<store.productSelections[].productSelection.id>)` |
| store to channel | `/channels?where=id in (<supplyChannels + distributionChannels ids>)` |
| store to cart-discount | `/cart-discounts?where=stores(key="<key>")` (empty where when key missing: skip request) |
| store to customer | `/customers?where=stores(key="<key>")` |
| customer-group to customer | `/customers?where=customerGroup(id="<id>")` |
| product-selection to product | `/product-selections/{id}/products?expand=product` |
| product-selection to store | `/stores?where=productSelections(productSelection(id="<id>"))` |
| channel to store | `/stores?where=supplyChannels(id="<id>") or distributionChannels(id="<id>")` |
| associate to business-unit | `/business-units?where=inheritedAssociates(customer(id="<id>")) or associates(customer(id="<id>"))` |
| product to product-selection | `/products/{id}/product-selections?expand=productSelection` |
| product to standalone-price | `/standalone-prices?where=sku in (<master + variant skus>)` |
| product to category | `/categories?where=id in (<masterData.current.categories[].id>)` |

## Performance for large projects

- Never list a whole collection: 20 per type per request, "Load more" is explicit. Root totals come from the response (`total`).
- `in (...)` lists capped at 100 ids with `truncated` surfaced (spec). No request can exceed ~6 KB of URL.
- Treemap hard cap 200 tiles: with 5 child types x 40 loaded entities the layout stays instant; beyond that "Load more" is
  hidden for the type and a note shows "Showing first N of M". Layout is memoised on `(ids, width, height)`.
- Additional-data: local-first + concurrency 4 + cache + generation guard (D5); roughly 80 percent fewer requests than before.
- ResizeObserver callback is throttled by `requestAnimationFrame`; no layout on every pixel.
- Raw JSON in the drawer renders only while open (Drawer content is not mounted when closed).

## Risks / Trade-offs

- [`@visx/hierarchy` 4.0.0 is new (June 2026) or misbehaves in jest/React 19] -> task 1.3 spike; fallback ladder in D1 (nivo, recharts, direct `d3-hierarchy` with `transformIgnorePatterns`, hand-written).
- [Licence of a (transitive) dependency is not permissive] -> task 1.2 licence check; `d3-hierarchy@1` is BSD-3-Clause (accepted, permissive); anything else stops the change.
- [Proxy URL / error shape differ from assumption in tests] -> spike task 2.2 before writing real tests.
- [Local summaries differ from old request-based counts] -> they are derived from the same fields; compare on live data in 9.3; difference is an accepted improvement only if the local count is more accurate (e.g. no truncation at 20).
- [`view_customer_groups` vs `view_customers`] -> the live check in 9.3 reads the 403 body naming the scope; update `wire-routes-and-welcome` D4 table if needed.
- [Colour sharing confuses] -> legend and tooltips always carry the type name; types sharing a slot never appear together.
- [Same shared files as other changes (`package.json`, `src/i18n/data/*.json`, jest config)] -> small, line-level edits; re-run `npm run extract-intl` after merging, never hand-merge `core.json`.
- [Unchanged old limitation] Search is exact-match only (old behaviour); partial search would need `contains`-style predicates not available for all fields. Not in scope (QC4).
