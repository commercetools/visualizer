Glossary (read once):
- **Merchant Center (MC)**: commercetools' admin web app. Our app is a *Custom Application* that MC
  shows inside its own shell.
- **entryPointUriPath**: the first URL segment of our app, here `visualizer`. Full URL:
  `/<project-key>/visualizer/<page>`.
- **submenu link**: an entry in MC's left navigation, declared in `custom-application-config.mjs`.
- **OAuth scope**: a permission string such as `view_types`. The app declares the scopes it needs; MC's
  API proxy refuses (HTTP 403) any request needing a scope that is not declared.
- **View / Manage permission**: per-user MC permission for this app, exposed as `PERMISSIONS.View` and
  `PERMISSIONS.Manage` in `visualizer/src/constants.ts`. MC refuses to render the app without View.
- **react-router v5 `<Switch>`**: renders the FIRST `<Route>` whose path matches. A `<Route>` with no
  `path` matches everything, so it must be last.

## Decisions

### D1. Route order and matching
Insert the two routes **after** `custom-objects` and **before** the catch-all. Both use prefix matching
(no `exact`) so the page may later own sub-paths like `/entity-diagram/xyz`.
Why safe: react-router matches whole path segments, so `.../visualize-drilldown` cannot be captured by an earlier
route such as `.../states/:type?` or `.../subscription/:id` (those start with a different segment).
Alternative rejected: `<Redirect from="/visualize" ...>` for the old dangling `visualize` link - there
was never a page, so there are no bookmarks to preserve; the catch-all already shows Welcome.

### D2. The stray `visualize` Welcome card is dropped
`specs/001-welcome/spec.md` itself offers "restore a target or drop the card". Default from
The owner question Q1 is "exact old behaviour", but the old card never worked. We drop it and
document it (owner question Q14 below). Also drop `visualize` from `specs/001-welcome`.

### D3. Menu permission
The two new links use `permissions: [PERMISSIONS.View]` (uncommented). The five existing links keep their
commented-out `permissions` line untouched: the main menu link already requires View, and changing
existing behaviour is out of scope. Pre-`3d8e4ba`, two links required `Manage`; we deliberately do
not bring that back (both new pages are read-oriented).
Pitfall: the Entity Diagram saves layout data into a Custom Object (container `mc-link-data`). A View-only
user can open the page but a save would be refused by the API. That is the page's concern (change B must
disable "save" without Manage); D only lists it as a cross-check item (task 7.3).

### D4. OAuth scopes (least privilege)
Evidence for what each page reads (old code, `git show e7cb4c4^:...`):
- Drilldown: REST GET through the MC API proxy on `/business-units`, `/customers`, `/stores`, `/channels`,
  `/products`, `/categories`, `/product-selections`, `/cart-discounts`, `/standalone-prices`, `/customer-groups`.
- Entity Diagram: reads Custom Objects (containers `mc-custom-object-schema`, `mc-link-data`), product types and
  types; saves Custom Objects.

| Resource read | Scope | In config today? |
|---|---|---|
| business-units | `view_business_units` | yes |
| customers, associates | `view_customers` | yes |
| customer-groups | `view_customer_groups` if the live 403 check (task 7.3) shows `view_customers` is not enough | **conditional** |
| stores | `view_stores` | yes |
| channels, products, product types | `view_products` | yes |
| categories | `view_categories` | **add** |
| product-selections | `view_product_selections` | yes |
| cart-discounts | `view_cart_discounts` | **add** |
| standalone-prices | `view_standalone_prices` | **add** (was removed in `3d8e4ba`) |
| types | `view_types` | yes |
| custom objects (read) | `view_key_value_documents` | yes |

Scopes to **remove** (code that used them is gone: `use-quote-request.ts` was deleted in `e7cb4c4`; no hook under
`src/hooks/` touches orders or shopping lists): `view_orders`, `manage_orders`, `view_shopping_lists`,
`manage_shopping_lists`. (`manage_quote_requests` is already gone.) Prove it with grep in task 5.1 before deleting;
if grep finds a use, keep the scope and write why in a comment.
`manage_*` scopes stay as they are (each maps to a feature that writes).
Pitfall: the commercetools scope table is the authority. If task 5.3 or change F sees a 403 for a resource
the table did not predict, add exactly the scope named in the 403 message and update this table.
